# Data Persistence

## 😀 Overview

UFlow provides a simple and easy-to-use data persistence tool designed around the `PersistenceDataProcessor` architecture, supporting storage and retrieval across multiple data formats.

Currently supported storage types (`PlayerDataType`):
- **Json**: Text format
- **Binary**: Binary format with AES encryption support
- **PlayerPrefs**: Unity native key-value storage
- **Capture**: Screen capture

Without changing the existing save/read APIs, the persistence system now also supports version control and data migration:
- Declaring the current version of an `IPersistenceData` type
- Always using the default serializer for the selected storage type
- Migrating old data step by step after the first load
- Automatically re-saving upgraded data in the latest version

## 🛠️ Usage

### 1.✨ Define Data to Store

It is recommended to use `IPersistenceData` to mark persistent data classes:

```csharp
[Serializable]
public class PlayerSave : IPersistenceData
{
    public long Id;
    public string Name;
}
```

If you do not use versioning attributes yet, saving and loading still work normally, the current version defaults to `1`

This allows gradual adoption instead of forcing a one-shot migration of all save types.

### 2.💾 Data Saving

Use the generic `PlayerDataUtils` APIs for saving. You only need to specify `PlayerDataType` to choose the storage format.

**Synchronous Saving**

```csharp
public void SaveExample(PlayerSave data)
{
    PlayerDataUtils.Save(data, PlayerDataType.Json);
    PlayerDataUtils.Save(data, PlayerDataType.Binary, encrypt: true);
    PlayerDataUtils.Save("MySaveFile", data, PlayerDataType.Binary, encrypt: true);
}
```

**Asynchronous Saving**

`PlayerDataUtils` provides callback-based, coroutine-based, and `async/await` save flows.

```csharp
public void SaveAsyncExample(PlayerSave data)
{
    PlayerDataUtils.SaveAsync(data, PlayerDataType.Binary, success =>
    {
        if (success)
        {
            Debug.Log("Save successful");
        }
    }, encrypt: true);
}

public IEnumerator SaveAsyncCoroutineExample(PlayerSave data)
{
    var yieldInstruction = PlayerDataUtils.SaveAsYieldInstruction(data, PlayerDataType.Binary, encrypt: true);
    yield return yieldInstruction;
    bool result = yieldInstruction.Result;
    if (result)
    {
        Debug.Log("Save successful");
    }
}

public async void SaveAsyncAwaitExample(PlayerSave data)
{
    bool result = await PlayerDataUtils.SaveAsTask(data, PlayerDataType.Binary, encrypt: true);
    if (result)
    {
        Debug.Log("Save successful");
    }
}
```

The processors now write version envelopes automatically. Game code does not need new save signatures or manual version fields in the payload.

You can check whether data exists with `HasSave`:

```csharp
public void HasSaveExample()
{
    bool exists = PlayerDataUtils.HasSave<PlayerSave>(PlayerDataType.Json);
    Debug.Log("Data exists: " + exists);

    bool existsCustom = PlayerDataUtils.HasSave<PlayerSave>("MySaveFile", PlayerDataType.Binary);
    Debug.Log("Custom file data exists: " + existsCustom);
}
```

### 3.📂 Data Reading

**Synchronous Reading**

```csharp
public void ReadExample()
{
    PlayerSave save1 = PlayerDataUtils.Read<PlayerSave>(PlayerDataType.Json);
    PlayerSave save2 = PlayerDataUtils.Read<PlayerSave>("MySaveFile", PlayerDataType.Binary, decrypt: true);
}
```

**Asynchronous Reading**

As with saving, callback, coroutine, and `async/await` flows are available.

```csharp
public void ReadAsyncExample()
{
    PlayerDataUtils.ReadAsync<PlayerSave>(PlayerDataType.Json, data =>
    {
        Debug.Log("Read data: " + data.Name);
    });
}

public IEnumerator ReadAsyncCoroutineExample()
{
    var yieldInstruction = PlayerDataUtils.ReadAsYieldInstruction<PlayerSave>(PlayerDataType.Json);
    yield return yieldInstruction;
    PlayerSave data = yieldInstruction.Result;
    Debug.Log("Read data: " + data.Name);
}

public async void ReadAsyncAwaitExample()
{
    PlayerSave data = await PlayerDataUtils.ReadAsTask<PlayerSave>(PlayerDataType.Json);
    Debug.Log("Read data: " + data.Name);
}
```

When older data is loaded, the pipeline is:
- Read the stored version from the payload envelope
- Deserialize the payload directly into the current type first
- Apply migration steps to finish version-specific initialization and fixes
- If a migration step returns an instance of the current type, that returned instance becomes the input of the next step
- Re-save the upgraded data automatically

In most cases, game code still only needs the existing `Read<T>` / `ReadAsync<T>` APIs.

### 4.🆕 Version Control and Data Migration

#### 1. Declare the current version

Use `PersistenceDataVersionAttribute` to declare the current version of a type:

```csharp
[Serializable]
[PersistenceDataVersion(2)]
public class PlayerSave : IPersistenceData
{
    public long Id;
    public string Name;
    public int Level;
}
```

If the attribute is missing, the current version is treated as `1`.

#### 2. Default serialization strategy

This scheme no longer defines per-version serializer or deserializer tags. The processors always use the default read/write strategy of the selected storage type:

- `Json` and `PlayerPrefs`: `SerializeUtils.SerializeToJson` / `SerializeUtils.DeserializeFromJson`
- `Binary`: `SerializeUtils.SerializeToBinary` / `SerializeUtils.DeserializeFromBinary` by `Save` mode

`SerializeUtils.Safe` is designed for persistence evolution:
- Fields that still exist are matched by field identity
- Removed fields are skipped
- Newly added fields keep their default values

It still cannot automatically solve field renames, semantic changes, or same-name type changes. Those cases should be handled by migration methods.

#### 3. Declare migration steps

Use `PersistenceMigrationMethodAttribute` to define upgrades between versions.

- The method should be declared on the data type itself
- The method takes no parameters
- The method runs on the first instance produced by deserializing old data into the current type
- The return type can be `void` or the current data type itself
- Mutating the current instance in place is recommended; returning a replacement instance of the current type is also supported
- Migration runs step by step in version order

```csharp
[PersistenceMigrationMethod(1, 2)]
private void UpgradeV1ToV2()
{
    Level = Mathf.Max(1, Level);
}
```

```csharp
[PersistenceMigrationMethod(2, 3)]
private PlayerSave UpgradeV2ToV3()
{
    return new PlayerSave
    {
        Id = Id,
        Name = string.IsNullOrEmpty(Name) ? "Player" : Name,
        Level = Mathf.Max(Level, 1)
    };
}
```

#### 5. Full example

```csharp
[Serializable]
[PersistenceDataVersion(2)]
public class PlayerSave : IPersistenceData
{
    public long Id;
    public string Name;
    public int Level;

    [PersistenceMigrationMethod(1, 2)]
    private void UpgradeV1ToV2()
    {
        Level = Mathf.Max(1, Level);
    }
}
```

When an old Json save is loaded:
- The saved version is read from the envelope
- The system first deserializes the payload directly into the current `PlayerSave`
- `UpgradeV1ToV2` runs on that instance to fill in initialization required by the newer version
- The processor re-saves the upgraded result as version `2`

#### 6. Migration checks in the editor

The editor tool window validates whether the migration chain matches the current version of each data class.

The validation rules are:
- Only instantiable types implementing `IPersistenceData` are checked
- If the current version is greater than `1`, the system verifies that every starting version from `1` to `currentVersion - 1` has at least one `PersistenceMigrationMethodAttribute`
- Missing starting versions are reported as warnings in the tool window

For example:
- The current version is `3`
- Only `[PersistenceMigrationMethod(2, 3)]` is declared

The editor will warn that a migration method starting from version `1` is missing, because the upgrade path from version `1` is incomplete.

### 5.⚙️ PlayerPrefs

You can use PlayerPrefs to store simple values such as `int`, `float`, and `string`.

```csharp
PlayerDataUtils.SavePlayerPrefs("IntKeyName", 114514);
PlayerDataUtils.SavePlayerPrefs("FloatKeyName", 3.14159f);
PlayerDataUtils.SavePlayerPrefs("StringKeyName", "Hello UFlow!");

var intValue = PlayerDataUtils.ReadPlayerInt("IntKeyName", 0);
var floatValue = PlayerDataUtils.ReadPlayerFloat("FloatKeyName", 0f);
var stringValue = PlayerDataUtils.ReadPlayerString("StringKeyName", "DefaultString");
```

For complex objects implementing `IPersistenceData`, `PlayerPrefsProcessor` now also supports version headers and automatic migration.

### 6.📸 Screen Capture

Screen capture is independent from the generic data persistence API.

```csharp
public IEnumerator CaptureExample()
{
    yield return PlayerDataUtils.TakeCapture("Screenshot");
    yield return PlayerDataUtils.TakeCapture("CameraShot", new Rect(0,0,1920,1080), Camera.main);
}

public void LoadCaptureExample()
{
    Sprite sp = PlayerDataUtils.LoadCapture("Screenshot");

    PlayerDataUtils.LoadCaptureAsync("Screenshot", sprite =>
    {
        // Use sprite
    });

    PlayerDataUtils.DeleteCapture("Screenshot");
}

public IEnumerator LoadCaptureAsyncExample()
{
    var yieldInstruction = PlayerDataUtils.LoadCaptureAsYieldInstruction("Screenshot");
    yield return yieldInstruction;
    Sprite sp = yieldInstruction.Result;
}

public async void LoadCaptureAsyncAwaitExample()
{
    Sprite sp = await PlayerDataUtils.LoadCaptureAsTask("Screenshot");
}
```

### 7. Clear Saved Data

Use `Clear` to delete specific saved files:

```csharp
public void ClearSaveExample()
{
    PlayerDataUtils.Clear<PlayerSave>(PlayerDataType.Json);
    PlayerDataUtils.Clear<PlayerSave>("MySaveFile", PlayerDataType.Binary);
    PlayerDataUtils.DeleteCapture("Screenshot");
    PlayerDataUtils.ClearAll(PlayerDataType.PlayerPrefs);
    PlayerDataUtils.ClearCapture();
}
```

## 🚀 How to Customize Data Saving Methods

The system uses reflection to auto-register processors, so extending new storage formats is straightforward.

### 1. Extend the enum

Add a new value to `PlayerDataType`:

```csharp
public enum PlayerDataType
{
    // ... existing types
    Xml = 10
}
```

### 2. Create a processor

Create a class inheriting from `PersistenceDataProcessor` and decorate it with `[DataProcessor]`.

```csharp
using PowerCellStudio;
using System;

[DataProcessor(PlayerDataType.Xml)]
public class XmlDataProcessor : PersistenceDataProcessor
{
    public override string directoryName => "Xml";
    public override string extension => "xml";

    public override bool Save<T>(string saveKey, T data, bool encrypt)
    {
        return true;
    }

    public override T Read<T>(string saveKey, bool decrypt)
    {
        return default;
    }

    public override void SaveAsync<T>(string saveKey, T data, Action<bool> onComplete, bool encrypt)
    {
    }

    public override void ReadAsync<T>(string saveKey, Action<T> onComplete, bool decrypt)
    {
    }
}
```

### 3. Automatic activation

No manual registration is required. `PlayerDataUtils.Init()` scans `PersistenceDataProcessor` types with the `[DataProcessor]` attribute and registers them automatically.

```csharp
PlayerDataUtils.Save(data, PlayerDataType.Xml);
```

If your custom processor also needs version control and migration, follow the same internal flow:
- Call `SerializeStringPayload` / `SerializeBinaryPayload` while saving
- Wrap the payload with version information
- Call `DeserializeStringPayload` / `DeserializeBinaryPayload` when reading
- Run `TryUpgradeData` after deserialization

## Data Conversion

In some cases, you may need to convert data between storage formats, or keep a one-time project-wide migration path separate from per-type version evolution. UFlow still provides `DataTranslator` for that purpose.

### 1. When to use `DataTranslator`

Use the two mechanisms for different problems:
- **Version evolution inside the same storage type**: prefer the version control and migration mechanism described above
- **Whole-format conversion between storage types**: use `DataTranslator`

Examples:
- `Json v1` to `Json v2`: prefer `PersistenceDataVersion` plus migration methods
- Converting an older project from `Json` saves to `Binary` saves: use `DataTranslator`

### 2. Use `DataTranslator`

UFlow provides `IDataTranslator` and `DataTranslatorBase` for implementing storage-format conversions.

```csharp
public class JsonToBinaryTranslator : DataTranslatorBase
{
    protected override string saveKey => GetType().Name;

    public override int version => 0;

    private BinaryDataProcessor _binaryDataProcessor = new BinaryDataProcessor();
    protected override PersistenceDataProcessor targetProcessor => _binaryDataProcessor;

    protected override object ReadOldData(string filePath, bool decrypt)
    {
        var jsonEn = File.ReadAllText(filePath);
        object result = null;
        try
        {
            if (decrypt)
            {
                var json = EncryptUtils.AESDecrypt(jsonEn, ConstSetting.FileEncryptionKey);
                result = JsonConvert.DeserializeObject(json);
            }
            else
            {
                result = JsonConvert.DeserializeObject(jsonEn);
            }
        }
        catch (Exception e)
        {
            LinkLog.LogError($"Failed to read json data: {e.Message}");
        }

        return result;
    }
}
```

### 3. Automatic activation

Once the translator class exists in the project, UFlow will detect and execute it automatically during initialization.

## Tool Window

UFlow provides an editor tool window for managing and debugging persistence data.

In the Unity Editor:
1. Open `Tool` -> `Editor Setting Window`
2. Select the `Data Persistence Data` tab

The window supports the following operations.

### Clear Data

- **Clear Player Prefs**: clears all data stored in `PlayerPrefs`
- **Clear Json**: clears all Json files
- **Clear Binary**: clears all Binary files
- **Delete All Capture**: deletes all capture files
- **Delete All**: clears Json, Binary, PlayerPrefs, and captures

### Read Data

1. **Search data**
   - Enter the save key in `Data Save Key`
   - Enable `Decrypt Data` if the data is encrypted
   - If no custom key is used, the default key is `{NamespaceName}_{TypeName}`

2. **Read operation**
   - Click `Read` to inspect saved data
   - Successfully read content is displayed as formatted text
   - Each entry includes a `Delete` button

3. **Load capture**
   - Enter the capture key in `Data Save Key`
   - Click `Load Capture` to load and preview the image

### Migration configuration warnings

If a persistence data type declares a higher current version but does not provide migration methods for the required starting versions, the tool window shows a warning at the top.

This check only validates migration chain coverage. It does not prove that the migration logic itself is correct.

## ✅ Recommended Scenarios

- Keep using the existing `PlayerDataUtils` API while adding version control to save data
- Build maintainable upgrade chains for Json, Binary, and PlayerPrefs object data
- Automatically migrate and re-save old data on read
- Use `DataTranslator` only when format-level conversion is actually needed
