# Binary Serialization System

## 😀 Overview

The binary serialization system is used to serialize runtime objects into compact binary byte streams and quickly deserialize them back into object instances when needed.

This system is built on type formatters, collection type inference, custom type selectors, and LZ4 compression. It is suitable for scenarios such as configuration caching, save data, runtime snapshots, offline data packaging, and similar workflows.

Main components are listed below:

| Component | Purpose |
|---|---|
| `BinarySerializer` | Public entry point for serialization and deserialization. |
| `BinaryFormatterResolver` | Selects the corresponding formatter based on the target type. |
| `BinarySerializeTypeBuffer` | Caches field layouts, instance constructors, collection type information, and custom selectors. |
| `IBinaryData` | Allows a type to provide custom binary write/read logic. |
| `IBinarySerializerTypeSelector` | Registers dedicated read/write handlers for special types. |
| `BinarySerializerTypeSelector<T>` | Generic base class for custom selectors, making strongly typed extensions easier to implement. |
| Various `Formatter`s | Handle concrete serialization logic for primitive types, arrays, collections, objects, enums, and more. |

Component dependencies
```
BinarySerializer
    |
    └──> BinaryFormatterResolver
            |
            |──> BinarySerializeTypeBuffer
            |       |
            |       |──> Custom TypeSelector registry
            |       └──> Field layout / constructor / collection metadata cache
            |
            |──> IBinaryData
            |
            └──> Various Formatter
                    |
                    ├──> Primitive type Formatter
                    ├──> Array / collection Formatter
                    ├──> CustomSelectorFormatter
                    └──> ObjectFormatter
```

## 🛠️ Usage

### 1.✨ **Serialize an object**

Use `BinarySerializer.Serialize<T>` to serialize an object into a byte array. The serialized result is first written into a binary stream and then compressed with LZ4.

```csharp
[Serializable]
public class PlayerProfile
{
    public int Id;
    public string Name;
    public List<int> Scores;
}

var profile = new PlayerProfile
{
    Id = 7,
    Name = "Hero",
    Scores = new List<int> { 10, 20, 30 }
};

byte[] bytes = BinarySerializer.Serialize(profile);
```

### 2.🔁 **Deserialize an object**

Use `BinarySerializer.Deserialize<T>` to restore a byte array into the target type.

```csharp
PlayerProfile profile = BinarySerializer.Deserialize<PlayerProfile>(bytes);
```

### 3.🔤 **Change string encoding**

The default encoding is `UTF8`. If your use case requires it, you can switch to another encoding before use.

```csharp
BinarySerializer.Encoding = Encoding.UTF8;
```

> Note: Serialization and deserialization of the same data must use the same encoding configuration.

## 🌟 Extension points

### 1. Use `IBinaryData` for custom binary read/write

If a type wants to fully control its own serialization process, it can implement `IBinaryData`.

```csharp
public struct ItemSnapshot : IBinaryData
{
    public int Id;
    public float Weight;

    public void ToBinary(BinaryWriter writer, Encoding encoding)
    {
        writer.Write(Id);
        writer.Write(Weight);
    }

    public void FromBinary(BinaryReader reader, Encoding encoding)
    {
        Id = reader.ReadInt32();
        Weight = reader.ReadSingle();
    }
}
```

At runtime, such types are handled through `BinaryDataTypeSelector<T>` first, rather than the default reflected object-field path.

### 2. Use `IBinarySerializerTypeSelector` to register handlers for special types

If you do not want to modify the target type itself, or if you need custom read/write logic for third-party types, you can register a custom TypeSelector.

It is recommended to inherit from `BinarySerializerTypeSelector<T>`:

```csharp
public sealed class CustomEncodedValueSelector : BinarySerializerTypeSelector<CustomEncodedValue>
{
    public override void Write(BinaryWriter writer, CustomEncodedValue value, Encoding encoding)
    {
        writer.Write(value.Number);

        byte[] bytes = encoding.GetBytes(value.Text ?? string.Empty);
        writer.Write(bytes.Length);
        writer.Write(bytes);
    }

    public override CustomEncodedValue Read(BinaryReader reader, Encoding encoding)
    {
        int number = reader.ReadInt32();
        int length = reader.ReadInt32();
        string text = encoding.GetString(reader.ReadBytes(length));

        return new CustomEncodedValue
        {
            Number = number,
            Text = text
        };
    }
}

BinarySerializer.RegisterCustomSelector(new CustomEncodedValueSelector());
```

### 3. Built-in support for special types

The following special type selectors are registered by default when the system starts:

- `IntPtr`
- `UIntPtr`
- `Guid`
- `TimeSpan`
- `DateTimeOffset`

These types use built-in TypeSelectors first rather than the default reflected object-field path.

## 📦 Supported type range

Based on the current implementation and test coverage, the system supports the following common types:

### 1. Primitive types

- `bool`
- `byte` / `sbyte`
- `short` / `ushort`
- `int` / `uint`
- `long` / `ulong`
- `float`
- `double`
- `decimal`
- `char`
- `string`
- `DateTime`
- `enum`

### 2. Common value types

- `Guid`
- `TimeSpan`
- `DateTimeOffset`
- Other value types that implement `IBinaryData` or have a registered selector

### 3. Arrays and collections

- one-dimensional arrays `T[]`
- `List<T>`
- `Dictionary<TKey, TValue>`
- `HashSet<T>`
- `Queue<T>`
- `Stack<T>`
- `KeyValuePair<TKey, TValue>`
- Fields declared as `IList<T>`, `ICollection<T>`, `IDictionary<TKey, TValue>`, or `ISet<T>` are also automatically mapped to usable concrete collection types

### 4. Plain objects

Ordinary objects are serialized through `ObjectFormatter<T>`, and the system reads instance fields recursively.

Supported content includes:

- public instance fields
- private instance fields marked with `[SerializeField]` in Unity
- nested objects
- nested collections
- reference-type fields whose value is `null`

## ⚙️ Internal mechanisms and optimizations

### 1. Type formatter cache

`BinaryFormatterResolver` caches the corresponding `IBinaryFormatter` for each type to avoid repeated reflection and formatter creation.

### 2. Field layout cache

`BinarySerializeTypeBuffer` caches:

- type field layouts
- instance constructors
- generic collection metadata
- collection helper methods such as `Enqueue` and `Push`
- custom TypeSelector mappings

This reduces repeated reflection and runtime allocations.

### 3. Automatic materialization of collection interfaces

When a field is declared as an interface type, the system attempts to map it to a default concrete implementation:

- `IList<T>` / `ICollection<T>` -> `List<T>`
- `IDictionary<TKey, TValue>` -> `Dictionary<TKey, TValue>`
- `ISet<T>` -> `HashSet<T>`

### 4. LZ4 compression

After `BinarySerializer.Serialize<T>` completes object writing, it applies LZ4 compression; `Deserialize<T>` first decompresses the data and then enters the deserialization pipeline.

This reduces persistence size, but it also means the serialized result is not a raw binary stream. It is a compressed byte array.

## 🔍 Example scenarios

### 1. Round-trip serialization of a plain object

```csharp
[Serializable]
public class ConfigData
{
    public int Id;
    public string Name;
    public Dictionary<string, int> Stats;
}

var source = new ConfigData
{
    Id = 1,
    Name = "ConfigA",
    Stats = new Dictionary<string, int>
    {
        { "hp", 100 },
        { "mp", 50 }
    }
};

byte[] bytes = BinarySerializer.Serialize(source);
ConfigData clone = BinarySerializer.Deserialize<ConfigData>(bytes);
```

### 2. Using interface fields to hold collections

```csharp
[Serializable]
public class InterfaceCollectionContainer
{
    public IList<int> Items;
    public IDictionary<string, int> Mappings;
    public ISet<string> Tags;
}
```

Such interface fields are restored to their default concrete collection implementations during deserialization.

### 3. Handling Unity private serialized fields

```csharp
[Serializable]
public class PrivateFieldContainer
{
    [SerializeField]
    private int _hiddenNumber;
}
```

In a Unity environment, fields like this are included in the serialization field list.

## ⚙️ Key interfaces

### `BinarySerializer` common methods

- `Serialize<T>(T obj)`
  - Writes the object into a binary stream and applies LZ4 compression.
- `Deserialize<T>(byte[] data)`
  - Decompresses the byte array and restores the target object.
- `RegisterCustomSelector(IBinarySerializerTypeSelector selector)`
  - Registers a custom type handler.

### `IBinaryData`

- `ToBinary(BinaryWriter writer, Encoding encoding)`
- `FromBinary(BinaryReader reader, Encoding encoding)`

### `IBinarySerializerTypeSelector`

- `TargetType`
- `Write(BinaryWriter writer, object value, Encoding encoding)`
- `Read(BinaryReader reader, Encoding encoding)`

### `IBinarySerializerTypeSelector<T>`

- `Write(BinaryWriter writer, T value, Encoding encoding)`
- `Read(BinaryReader reader, Encoding encoding)`

### `BinarySerializerTypeSelector<T>`

- Provides a generic base class for custom TypeSelectors and is the recommended starting point for custom implementations.

## ℹ️ Notes

1. The root type cannot be an interface, an abstract class, or an open generic type.
2. `UnityEngine.Object` and its derived types are not directly supported by this serialization utility.
3. During deserialization of ordinary reference types, a callable parameterless constructor is preferred. If there is no parameterless constructor, the type must be explicitly marked with `[Serializable]` so the system can fall back to using an uninitialized object.
4. Field serialization is based on fields rather than properties. Whether an auto-property backing field is included depends on its field visibility and whether it passes the field filtering rules.
5. String encoding comes from `BinarySerializer.Encoding`; serialization and deserialization must use the same configuration.
6. If a type provides both `IBinaryData` and `IBinarySerializerTypeSelector`, the current resolution order prefers `IBinaryData`.
7. Custom selector registration is usually best completed during system initialization, avoiding dynamic changes to the handling strategy of the same type during serialization.

## ✅ Recommended scenarios

- Binary caching of configuration objects
- Local save or snapshot data
- Offline data packaging that needs smaller storage size
- Scenarios where specific types must take over low-level read/write behavior
- Scenarios where Unity runtime needs to quickly reconstruct structured object data
- Network messages requiring serialized payloads
